# web/src/components

Four panels, each a `mountXxx(root: HTMLElement, ...)` function called once from `main.ts`. No framework: each renders its markup via a template-string `innerHTML` assignment, then wires up plain `addEventListener` calls — there's no virtual DOM or reactive re-render, so a component that needs to update in response to state generally re-queries/mutates specific elements it already grabbed a reference to, rather than re-rendering wholesale.

- **`directoryBrowser.ts`** — drive `<select>` + breadcrumb + entry list. Clicking a directory calls `api.browse` again; clicking a video sets the shared `selectedVideo` store (from `../state.ts`) rather than tracking selection locally, since `jobConfigPanel` needs to read it too. Selected-row highlighting is done by comparing `dataset.path` against the store's current value in a `selectedVideo.subscribe` callback, not by tracking DOM node identity.
- **`jobConfigPanel.ts`** — model/language dropdowns (populated from `api.models()`/`api.languages()`), output-mode radios (toggling the custom-directory `<input>`'s `disabled` state), a collapsible advanced `-ml`/max-len field, and the submit button that calls `api.createJob` and sets `activeJobId`. Validates client-side (video selected? model selected?) before calling the API, but the server re-validates everything anyway (see `internal/httpapi/CLAUDE.md`) — this is just for a faster/friendlier error, not the actual guarantee.
- **`progressPanel.ts`** — subscribes to `activeJobId`; each change tears down any previous `subscribeJobEvents` subscription and opens a new one (or shows the empty state if `null`). The cancel button calls `api.cancelJob` — note it does *not* optimistically update the UI, it waits for the resulting `"canceled"` SSE event to actually change the displayed state.
- **`jobHistory.ts`** — refreshes two ways: automatically whenever `activeJobId` changes (via its own subscription, which also handles the initial load), *and* via explicit `onJobCreated`/`onJobFinished` callbacks passed in from `main.ts`. The explicit callbacks aren't redundant with the `activeJobId` subscription — a job reaching a terminal state (done/failed/canceled) doesn't change *which* job is active, so without `onJobFinished` the history list's displayed status/percent for that row would go stale until something else happened to change `activeJobId`.

If you add a fifth panel, follow the same shape (a `mountXxx` function, own file, reads/writes `../state.ts` for anything cross-panel) rather than introducing a different pattern.
