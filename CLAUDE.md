# faster-whisper-gui

A local, single-user Windows tool: Go backend + Vite/TypeScript frontend that transcribes video or audio files into SRT subtitle files using whisper.cpp, saved next to each source file by default. See [README.md](README.md) / [README.zh-CN.md](README.zh-CN.md) for user-facing setup/usage docs — this file is oriented at whoever (human or AI) is editing the code.

## Architecture at a glance

- **Transcription engine**: whisper.cpp, invoked as a subprocess (`whisper-cli.exe`), not Python's faster-whisper or a cgo binding. See internal/transcribe and internal/procutil below for why (no Python/CUDA userland to install; no C/C++ toolchain needed to build this repo; a whisper-cli crash can't take the Go process down with it).
- **Media selection**: a server-side file browser (`internal/fsbrowse`), because a browser's native file picker/drag-and-drop can't hand back an absolute local path, and "save next to the source file" needs that absolute path. The frontend lets several video/audio files be checked at once and submits one job per file, sharing a single model/language/output config.
- **Batch jobs, serial execution**: `internal/job.Queue` runs exactly one job at a time regardless of how many were submitted together — a single GPU can't usefully run concurrent whisper-cli processes. The frontend's per-job Progress tabs only visualize several jobs' states side by side; they don't parallelize execution.
- **Progress reporting**: SSE, primarily derived from whisper-cli's own per-segment stdout timestamps divided by the audio duration, not its own (historically buggy) stderr percentage line.
- **Save is additive, not a rewrite**: the `.srt` is written to its real destination the moment a job finishes, exactly as it always has been. `POST /api/jobs/{id}/export` (`internal/fsbrowse.CopyFile`) only copies an already-finished job's `.srt` to a second, user-chosen folder on demand — it never changes where the original was written.
- **User-configurable paths**: `internal/settings` persists optional overrides (ffmpeg/whisper-cli paths, models directory, default media directory) as `<root>/settings.json`; `internal/config`'s `Effective*` methods layer those overrides on top of the `bin/`/`models/` conventional defaults, so a Settings-panel change takes effect on the next job with no restart.
- **Process robustness**: every subprocess (ffmpeg, whisper-cli, and in `cmd/dev`, bun/vite) is bound to a Windows Job Object, so canceling a job — or this program crashing — can't leave an orphaned process behind. This is the single most load-bearing piece of Windows-specific plumbing in the codebase; see internal/procutil below before touching any subprocess code.
- **Packaging**: the built frontend is embedded into the Go binary via `go:embed` (see internal/webui below) — the shipped artifact is a single `.exe`.
- **Windows only.** Nothing here has been made cross-platform, and several packages (`fsbrowse`, `procutil`) use Windows-specific APIs directly.

## Cross-cutting conventions worth knowing before editing

- The server binds `127.0.0.1` only, never `0.0.0.0` — the file-browser API exposes real filesystem paths and must never be reachable off-box.
- Any path arriving from the frontend (a hand-typed custom output directory, a Settings-panel override, in particular) gets `filepath.Clean(filepath.FromSlash(p))` before use — see `internal/fsbrowse.ValidateAbsDir`/`ValidateMediaFile`/`ValidateExeFile` and `internal/job.OutputPrefix`.
- Nothing sets `http.Server.WriteTimeout` — deliberately. It's a fixed deadline from when headers finish reading, not reset by ongoing writes, and would kill a long SSE connection during a multi-minute transcription. `ReadHeaderTimeout` is set instead (safe: doesn't touch response duration).
- `internal/job`'s `Store.Get` returns a value copy of `Job`, never the live pointer — the worker goroutine mutates jobs in place under a lock, so handing out the pointer would race any caller reading it afterward.
- `PUT /api/settings`'s request fields are all `*string`, not `string` — this is how the handler tells "field absent from the JSON body" (leave that override untouched) apart from "field present as `\"\"`" (explicitly clear it back to the conventional default). If you add a new user-configurable path, follow this pattern rather than a plain string with `omitempty`.
- Package manager is **bun**, not npm (see web/ below and the root `.gitignore`, which ignores a stray `package-lock.json` in case npm gets run by mistake).

## Directory reference

Detailed, per-package notes for whoever is editing the code — organized `cmd/` → `internal/` (roughly bottom-up dependency order, lower items depend on higher ones) → `web/`.

### cmd/

Two entrypoints, both thin wrappers around internal/appserver (see below) so the actual HTTP wiring exists in exactly one place:

- **cmd/server** — the production build. `go build ./cmd/server` produces the single `.exe` end users run; it embeds the frontend via `internal/webui` and just calls `appserver.New(cfg)` then `ListenAndServe()`.
- **cmd/dev** — a developer convenience only, not shipped to end users. Runs the same Go backend (in a goroutine, so it can be gracefully `Shutdown`) alongside a `bun run dev` (Vite) subprocess, so day-to-day frontend work doesn't need two terminals.

If you change how the server is constructed (routes, middleware, config wiring), do it in `internal/appserver`, not in either `main.go` — that's the whole point of the split.

#### cmd/server

Production entrypoint. `go build ./cmd/server` yields the single `.exe` end users double-click.

`main.go` does, in order: parse `-root`/`-addr` flags → `config.Load` → `cfg.CleanTmpDir()` → `appserver.New(cfg)` → log the listen address → `srv.ListenAndServe()`. That's the whole file — all actual route/middleware/pipeline wiring lives in internal/appserver (see below), shared with `cmd/dev`. Don't add logic here beyond flag parsing; put it in `appserver` instead so `cmd/dev` gets it too.

`-root` defaults to `""`, which `config.Load` resolves to the executable's own directory via `os.Executable()` — correct for a double-clicked `server.exe`, but note this is *wrong* under `go run` (which compiles to a temp path). If you need to `go run ./cmd/server` for a quick manual test, pass `-root <repo-root>` explicitly (see how the plan/session history did this during development). `cmd/dev` sidesteps this entirely by defaulting `-root` to the current working directory instead, since it's meant to be run via `go run`.

#### cmd/dev

Developer convenience only — not what end users run (that's `cmd/server`). `go run ./cmd/dev`, executed from the repo root, starts both halves of the stack from one command:

- The Go backend, built via the same `appserver.New(cfg)` as `cmd/server`, run via `srv.ListenAndServe()` inside a goroutine so it can be `Shutdown` gracefully later.
- A `bun run dev` (Vite) subprocess, started through `internal/procutil.Start` (Job-Object-managed, not a bare `exec.Cmd`) with `Stdout`/`Stderr` wired directly to the parent's — logs from both processes interleave in one terminal, prefixed `[go]`/`[vite]`.

Shutdown is triggered by `signal.NotifyContext(context.Background(), os.Interrupt)` (Ctrl+C): `srv.Shutdown(ctx)` for the HTTP server, then `vite.Stop()` + `vite.Wait()` for the subprocess — `Stop()` calls `TerminateJobObject`, which kills the whole tree bun/vite spawned (confirmed by hand: killing the compiled `dev.exe` outright, simulating a crash, still takes the entire `bun.exe`→`node.exe` chain down via the Job Object's kill-on-close semantics, without this shutdown code ever running).

**Two things worth knowing if you touch this file:**

1. `-root` defaults to `os.Getwd()`, *not* the executable's directory (unlike `cmd/server`). This is deliberate: `go run` compiles to a temp path, so the `cmd/server` convention of resolving relative to the executable would silently break here. This does mean `cmd/dev` must be launched from the repo root (or with an explicit `-root`) for `web/` to be found.
2. If `-addr` overrides the backend port, `FASTER_WHISPER_GUI_BACKEND_ADDR` is set in the spawned bun process's environment so `web/vite.config.ts`'s dev-proxy target follows automatically — without this, Vite would keep proxying `/api` to the hardcoded default and every request would 502. If you add more config that needs to flow from Go to the Vite dev server, extend this same env-var pattern rather than hand-editing `vite.config.ts` per environment.

This file spawns `bun run dev`, not the bare `bun dev` shorthand — the bare form would actually work fine here (`dev` isn't one of bun's own subcommand names), but `run` is used consistently everywhere in this repo since the sibling `build` script *does* collide with bun's built-in bundler (see web/ below), and it's simpler to never rely on the shorthand being safe than to remember which script names happen to be exceptions.

### internal/

All real logic lives here; `cmd/` is just entrypoints. Roughly bottom-up dependency order (lower items depend on higher ones):

1. **internal/procutil** — Windows subprocess plumbing (Job Object lifecycle, `\r`/`\n`-aware line scanning). No dependencies on anything else here; everything else that spawns a process depends on this.
2. **internal/settings** — persists user-chosen path overrides (ffmpeg/whisper-cli/models directory) as `<root>/settings.json`. No dependencies.
3. **internal/config** — resolves the on-disk layout (`bin/whisper`, `bin/ffmpeg`, `models/`, `tmp/`) into absolute paths, and layers `settings` overrides on top via its `Effective*` methods. Depends on `settings`.
4. **internal/transcribe** — the media→wav→srt pipeline pieces (ffmpeg invocation, the `Engine` interface, `WhisperCppEngine`, health checks, model scanning). Depends on `procutil`.
5. **internal/fsbrowse** — exposes the local filesystem to the frontend (drive/directory listing, path validation/normalization). No dependencies on the above.
6. **internal/sseutil** — a minimal per-job SSE pub-sub broker. No dependencies; `job` talks to it only through an interface `job` itself defines, to avoid a cycle.
7. **internal/job** — the job queue/state machine that drives `transcribe` and reports through something shaped like `sseutil.Broker`.
8. **internal/httpapi** — the REST/SSE handlers, wiring together `job`, `fsbrowse`, `transcribe` (for model listing), and `config` (including its `Settings` store, for the Settings panel's `GET`/`PUT /api/settings`).
9. **internal/webui** — `go:embed`s the built frontend. Independent of everything else; exists only because of where Go resolves embed paths from.
10. **internal/appserver** (one file, `appserver.go`, no subfolder) — the final assembly: builds the `*http.Server` from `httpapi` + `webui` + `job`/`sseutil`/`transcribe`/`config`. This is what both `cmd/server` and `cmd/dev` call.

Everything here targets Windows only — `fsbrowse` and `procutil` call `golang.org/x/sys/windows` directly, and `job`'s single-worker queue assumes a Job Object exists for cleanup, not POSIX process groups.

#### internal/procutil

Windows-specific subprocess plumbing, with no dependency on anything else in this repo. Every subprocess the codebase spawns (ffmpeg, whisper-cli, and in `cmd/dev`, `bun run dev`) should go through `Start` here, not a bare `cmd.Start()`. The primary consumer is `internal/transcribe`; cmd/dev above covers the bun/vite side.

- **`linesplit.go`** — `ScanCRLines`, a `bufio.SplitFunc` (used via `NewCRLineScanner`) that treats a bare `\r` as a line terminator in addition to `\n`. whisper-cli's and ffmpeg's progress output redraws in place using `\r` the way a classic CLI progress bar does; `bufio.ScanLines` only splits on `\n`, so those updates would sit in the buffer — invisible — until the next real `\n` arrives, which looks like "progress stalls for a few seconds then jumps." A `\r` immediately followed by `\n` is collapsed into a single CRLF terminator rather than emitting a spurious empty line, and a trailing bare `\r` with no more data coming (EOF) still counts as a terminator rather than being dropped — see `linesplit_test.go`'s CRLF and trailing-bare-`\r`-at-EOF cases. This is a pure, well-tested function — if progress parsing elsewhere seems to skip lines, check whether it's reading through this scanner or a plain one.
- **`jobobject_windows.go`** — `JobObject` wraps `CreateJobObject`/`SetInformationJobObject` (with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) / `AssignProcessToJobObject` / `TerminateJobObject`. The payoff: killing or closing the job takes down *every* process assigned to it, including grandchildren the direct child spawns — plain `cmd.Process.Kill()` only ever reaches the direct child. This has been verified by hand against a real multi-level tree (`dev.exe` → `bun.exe` → `node.exe`): force-killing the top process alone still cleans up the whole chain, because `KILL_ON_JOB_CLOSE` fires when the job handle is reclaimed on process exit, with no cooperation from the dying process required. Note `AssignProcessToJobObject` requires `PROCESS_SET_QUOTA|PROCESS_TERMINATE` access, obtained here via `OpenProcess` by PID immediately after `cmd.Start()` — not a flag on `CreateProcess` itself.
- **`managed_windows.go`** — `ManagedProcess`/`Start(cmd)` ties the two together: starts `cmd`, creates a `JobObject`, assigns the new process to it. If job-object creation/assignment fails (e.g. this program is itself running inside some restrictive parent job/container that denies nesting), it logs a warning and **degrades to plain `cmd.Process.Kill()`** rather than treating it as fatal — job-object cleanup is a safety net, not a correctness requirement, so a restricted environment shouldn't crash the whole program over losing it. `Close` is safe to call unconditionally after `Wait` returns, in degraded mode too — it's a no-op when there's no job object to release.

If you add a new subprocess call anywhere in the codebase, route it through `procutil.Start`, and if you need to read its output for progress/diagnostics, read it through `NewCRLineScanner` rather than a plain `bufio.Scanner`.

#### internal/settings

One file, `settings.go`, with no dependency on any other package here — kept one-directional (`internal/config` depends on this, not the reverse) so `config.Load` doesn't gain a cycle. `Store` persists user-chosen overrides (`Paths`: `FfmpegPath`, `WhisperCliPath`, `ModelsDir`, `DefaultVideoDir`, each JSON-tagged `omitempty`) to `<root>/settings.json`, letting the web UI point at binaries/models that live outside the conventional `bin/whisper`, `bin/ffmpeg`, `models` layout `internal/config` resolves by default.

An empty `Paths` field means "no override, use the default" — this package has no concept of what the conventional defaults *are*, that's `internal/config`'s job via its `Effective*` methods. `Paths` is deliberately only two-state (set/unset) per field: the three-state "field absent from the request vs. present as `""` vs. present as a real path" distinction that `PUT /api/settings` needs lives at the HTTP layer, not here — see `internal/httpapi`'s `settings_handlers.go`, whose request struct uses `*string` fields for exactly that. Don't try to encode that tri-state into `Paths` itself if you touch this. `DefaultVideoDir` is the odd one out semantically: it has no conventional default to fall back to (see `internal/config`'s `EffectiveDefaultVideoDir`), it's purely "which directory should the media picker open to" and defaults to unset (picker lists all drives). Its name keeps the pre-audio-support "Video" wording on purpose — see internal/config below for why it wasn't renamed alongside `fsbrowse`'s video→media rename.

`Load` treats a missing file as "nothing saved yet" (zero-value `Paths`, no error) but a file that exists and fails to parse *is* an error — a corrupted `settings.json` should surface at startup, not silently discard whatever the user last saved.

`Set` writes atomically: marshal to a temp file in the same directory (`os.CreateTemp`), then `os.Rename` it over `settings.json` (atomic on the same volume), and only updates the in-memory value `Get` returns after the rename succeeds. If anything fails before the rename, the temp file is removed explicitly — a failed save should never leave stray `.settings-*.tmp` files behind, and never touches the previously-saved `settings.json`.

`Store` is safe for concurrent `Get`/`Set` (a `sync.RWMutex`) — `Get` is called on essentially every request (`GET /api/settings`, job creation, health checks, model scans) while a save could land from a concurrent `PUT /api/settings`.

#### internal/config

One file, `config.go`, depends on `internal/settings`. `Config` holds every resolved *absolute* path the rest of the app needs: `WhisperCliPath`, `FfmpegPath`, `FfprobePath`, `ModelsDir`, `TmpDir`, plus `Addr`. These fields are the **conventional defaults** (`bin/whisper`, `bin/ffmpeg`, `models`, all relative to `Root`) — nothing else in the codebase should compute these paths itself, always go through this struct.

`Config` also holds a `Settings *settings.Store`, which lets the web UI override where ffmpeg/whisper-cli/models actually live. **Callers resolving where to actually find a binary or the models directory must call the `Effective*` methods — `EffectiveFfmpegPath`, `EffectiveFfprobePath`, `EffectiveWhisperCliPath`, `EffectiveModelsDir` — never the plain fields directly.** (`internal/appserver`'s engine/pipeline wiring and `internal/httpapi`'s health/models/job handlers are the real callers — this is what lets a Settings-panel change take effect on the very next job with no restart, since each `Effective*` call re-reads `cfg.Settings` fresh.) Each falls back to the corresponding conventional-default field when no override is set. `EffectiveFfprobePath` is derived rather than independently overridable: if `FfmpegPath` is overridden, ffprobe.exe is assumed to live right next to it (`filepath.Dir(override)/ffprobe.exe`), since every ffmpeg distribution ships both binaries together — this avoids needing a fourth settings field just for ffprobe. `EffectiveDefaultVideoDir` is different from the rest: there's no conventional default backing it (it just returns `Settings.Get().DefaultVideoDir`, `""` when unset), since it only controls which directory `directoryBrowser.ts`'s media picker opens to on load, not something the transcription pipeline needs. The `Video` in its name and in `settings.DefaultVideoDir` is a naming holdover from before audio files were supported — deliberately *not* renamed alongside the rest of the video→media rename, since it's persisted to `settings.json` and renaming the JSON key would silently drop an existing user's saved override on upgrade.

`Load(root)` resolves `root` to `filepath.Dir(os.Executable())` when called with `""`, then `os.MkdirAll`s `bin/whisper`, `bin/ffmpeg`, `models`, and `tmp` unconditionally, then loads `<root>/settings.json` via `settings.Load` into `Settings`. That `MkdirAll` matters: it means every other package (`fsbrowse`'s directory scans, `transcribe.ScanModels`, the job queue's temp-file writes) can assume these directories exist and never has to special-case `os.ErrNotExist` on a fresh checkout. `Load` returns an error both when directory creation fails and when `settings.json` exists but fails to parse — a corrupted settings file is meant to surface loudly at startup, not be silently ignored.

`CleanTmpDir()` wipes everything inside `TmpDir` — called once at startup by both `cmd/server` and `cmd/dev` to clear scratch WAV files left behind by a previous run that crashed before `internal/job`'s own per-job cleanup ran.

**Gotcha if you add a new caller of `Load`:** the `""` → `os.Executable()` default is correct for a built `.exe` but resolves to a *temp build directory* under `go run`. `cmd/server` accepts this (it's meant to be built, not `go run`); `cmd/dev` explicitly overrides it to `os.Getwd()` instead because it's meant to be `go run` from the repo root. Pick the right default for whatever you're adding, don't just copy one or the other blindly.

#### internal/transcribe

The media (video or audio) → wav → srt pipeline pieces. Everything here shells out via `internal/procutil` — never cgo, see internal/procutil above and the top of this file for why (no C/C++ toolchain to build this repo with, a whisper-cli crash can't take the Go process down, swapping CPU/CUDA builds is just swapping files in `bin/whisper/`).

- **`engine.go`** — the `Engine` interface (`Transcribe(ctx, Options, onProgress) error`) and its `Options`/`Progress` types. This is the extension point for a hypothetical future faster-whisper-as-subprocess engine — `internal/job`'s queue only depends on this interface, not on `WhisperCppEngine` directly, so a second implementation could be swapped in without touching the queue.
- **`whispercpp.go`** — `WhisperCppEngine`, the only current `Engine` implementation. `BuildWhisperArgs` is a pure function (easy to unit test) building the `whisper-cli` argv; language defaults to `"auto"` if empty. `Transcribe` reads stdout and stderr concurrently through `procutil.NewCRLineScanner`: **stdout's per-segment timestamps are the primary progress signal** (end-timestamp ÷ `Options.TotalDuration`), stderr's own `progress = NN%` line is only a secondary/supplementary one, because whisper.cpp's own percentage reporting has real documented reliability problems (a divide-by-zero SIGFPE, progress appearing stuck on long files) — don't flip this priority. `CliPath` is `func() string`, not a plain string — the one `WhisperCppEngine` instance is constructed once in `internal/appserver` and reused for every job, so a plain string would freeze whatever path was configured at process startup; `appserver` wires it to `(*config.Config).EffectiveWhisperCliPath`, a method value, so a Settings-panel change takes effect on the very next job with no restart needed. `BuildWhisperArgs` always appends `-mc <Options.MaxContext>` (unlike `-ml`, which is only added `if opts.MaxLen > 0`) because `Options.MaxContext`'s Go zero-value (`0`) *is* the desired default here, not "unset" — whisper.cpp conditions each segment's decoding on all previously transcribed text by default (its own native `-mc` default is `-1`, unlimited), so one bad segment (typically triggered by silence, music, or background noise) can otherwise keep reinforcing itself for the rest of the file; defaulting to `-mc 0` disables that carryover so a single bad segment can't propagate.
- **`ffmpeg.go`** — `ExtractAudio` (media → 16kHz mono 16-bit PCM WAV; whisper.cpp cannot read video/audio containers directly, this is why ffmpeg is a required external dependency at all) and `ProbeDuration` (the exact `ffprobe -show_entries format=duration -of default=noprint_wrappers=1:nokey=1` incantation that makes it print a bare float to stdout, parsed with `strconv.ParseFloat`) — `format=duration` reads the container-level duration, so it works the same whether the input has a video stream or is audio-only. `ExtractAudioArgs`/`ProbeDurationArgs` are separated out as pure functions purely for testability — actual subprocess invocation isn't unit-tested, only argv construction.
- **`health.go`** — `CheckFfmpeg`/`CheckWhisperCli`, used by `GET /api/health` so a missing binary or DLL surfaces as a clear frontend message before a user submits a real job, not after. Short timeout (`healthCheckTimeout`), and note it doesn't special-case a missing-DLL failure — any non-zero exit or start failure just gets its stderr tail (or the raw error) surfaced as-is.
- **`models.go`** — `ScanModels`, a non-recursive scan of `models/` for `ggml-*.bin` files. Manual-placement only for now (see root README's "known limitations") — no download/checksum logic.

If you add a second `Engine`, it needs its own progress-derivation strategy; don't assume every future engine prints whisper.cpp-shaped stdout.

#### internal/fsbrowse

Everything about touching the local filesystem on the frontend's behalf lives here. This whole package exists because the tool's core feature (save the SRT next to the source file) requires an absolute local path, and a browser's native file picker/drag-and-drop will never hand one back — so instead the server browses the disk itself and the frontend just renders what it returns.

- `ListDrives()` — enumerates drive letters via `windows.GetLogicalDrives`/`GetDriveType`, skipping `DRIVE_NO_ROOT_DIR`/`DRIVE_UNKNOWN`.
- `List(dir)` — lists `dir`'s subdirectories and media (video/audio) files only (everything else filtered out; see `mediaExtensions`/`MediaKind`/`IsMediaFile`), directories first then alphabetical, case-insensitive. It's a thin wrapper: `ListFiltered(dir, MediaKind)`. Expects `dir` to already be absolute/cleaned — validate with `ValidateAbsDir` first, neither function re-checks.
- `ListFiltered(dir, kindOf)` — the general form `List` wraps. `kindOf(name)` returns the `Entry.Type` tag to use for a matching file, or `""` to exclude it — this is how `List` can tag entries `"video"` or `"audio"` individually rather than one fixed tag for every match. `httpapi`'s browse handler calls this directly for the Settings panel's file pickers: a `kindOf` that returns `"file"` for `IsExeFile` matches (browsing for ffmpeg.exe/whisper-cli.exe), and one that always returns `""` for a directories-only listing when picking the models directory override (there's nothing to click *within* the directory in that case).
- `ValidateAbsDir` / `ValidateMediaFile` / `ValidateExeFile` — the normalization boundary for any path arriving from the client. `ValidateMediaFile`/`ValidateExeFile` are both thin wrappers around the unexported `validateFile(p, match, what)`. All three run `filepath.Clean(filepath.FromSlash(p))` before validating, because free-typed fields (custom output directory, and now the Settings panel's path inputs) can contain forward slashes. Every HTTP handler that receives a path from the request should go through one of these, not `os.Stat` directly.
- `EnsureWritable(path)` — opens (creating if absent, never truncating existing content) then immediately closes `path`, used to fail a job submission fast if the target `.srt` is locked by something (e.g. a media player has it open). **Treat any non-nil error as "not writable"** — don't pattern-match `os.ErrPermission` specifically. Windows reports a locked file as a sharing violation, which is a different error than access-denied, so a narrow check would silently miss the single most common real-world case this function exists to catch.
- `CopyFile(src, dst)` — opens `src` and copies it into `dst` (creating or truncating), used by `httpapi`'s job-export handler to duplicate an already-finished job's `.srt` into a user-chosen folder on demand. This is a separate, additive action from the automatic write whisper-cli already does at job completion — `CopyFile` never touches `src`, and copying again over an existing `dst` overwrites it cleanly rather than appending.

Tests use `t.TempDir()` real-filesystem fixtures throughout, no mocking — see `fsbrowse_test.go` for the pattern if you add more path-handling functions here.

#### internal/sseutil

One file, `broker.go`, with no dependency on anything else in this repo. `Broker` is a minimal per-job pub-sub: each job ID is its own topic, and any number of HTTP handlers can `Subscribe` to receive that job's `Event`s (`Type` becomes the SSE `event:` field, `Data` is JSON-marshaled for `data:` by the handler) as `internal/httpapi`'s SSE handler forwards them to the client.

- `Subscribe(jobID)` returns a 32-buffered channel plus an `unsubscribe` func — **callers must call `unsubscribe`** (typically via `defer`) when done reading, or the channel and its map entry leak forever.
- `Publish` is **non-blocking/best-effort** (`select` with a `default`): a subscriber that hasn't drained its channel just misses the event rather than blocking the job pipeline. This means SSE progress is inherently lossy under backpressure — `GET /api/jobs/{id}` (via `internal/job.Store`) remains the source of truth for a job's current state if an SSE client needs to catch up, and `httpapi`'s SSE handler leans on this by sending the job's current state immediately on every new subscription rather than assuming the client saw everything.

`Broker` implements `internal/job`'s `EventPublisher` structurally (duck-typed) — `sseutil` doesn't import `job`, and `job` doesn't import `sseutil`. Keep it that way if you extend either package; the interface lives in `job` specifically so the queue package doesn't need to know anything about SSE as a transport.

#### internal/job

The job queue and state machine. Three files:

- **`job.go`** — `Status`/`OutputMode` enums, the `Request`/`Job` structs (with JSON tags for the API — `Request.ModelPath` is `json:"-"`, it's a local filesystem detail not part of the public shape), and `Store`, an in-memory thread-safe job history.
  - **`Store.Get` returns a value copy of `Job`, never the live `*Job`.** The worker goroutine mutates a job's fields in place under `Store`'s lock (`Update`); handing back the pointer instead of a copy would let a caller read it concurrently with no synchronization. If you add a new `Store` method, keep this invariant — copy out, don't leak the pointer.
  - **`Store.Cancel` checks `Status.IsTerminal()` and reads the cancel func together, under one lock**, before deciding whether to invoke it. This was a real bug once: an earlier version only checked "is there a cancel func at all" (true forever once a job starts, even after it finishes), so canceling an already-done job incorrectly succeeded (202 instead of 409). If you touch `Cancel`, keep the terminal-status check inside the same critical section as the read of `j.cancel`, not after — otherwise it races `Update` marking the job terminal.
- **`queue.go`** — `Queue` runs exactly one job at a time (a single GPU can't usefully run concurrent whisper-cli processes anyway) via one worker goroutine consuming a channel. `Pipeline.ExtractAudio`/`Pipeline.ProbeDuration` are **injected function fields**, not direct calls to `transcribe.ExtractAudio`/`transcribe.ProbeDuration` — this is deliberate so `queue_test.go` can fake them (and the `Engine`) to test sequencing/cancellation without spawning real ffmpeg/whisper-cli processes. `internal/appserver` (`appserver.go`) is the only place that wires the real `transcribe` functions in; don't collapse this back to a direct dependency just to "simplify" it, the tests rely on the seam.
- **`outputpath.go`** — `OutputPrefix(req)`, the pure function computing whisper-cli's `-of` argument: the source file's own directory + basename by default, or `OutputDir` + basename in custom mode, with only the *final* extension stripped (so `my.video.v2.mp4` → `.../my.video.v2`, not `.../my`) and both the media path and any custom output dir normalized via `filepath.Clean(filepath.FromSlash(...))` first. This is exported (not just package-private) specifically so `internal/httpapi`'s job handler can compute the same `.srt` path for the pre-submission writability check — keep it a pure function if you extend it, `httpapi` depends on that.

`EventPublisher` is an interface `job` defines itself (not imported from `sseutil`) purely to avoid `job` depending on the SSE transport — `sseutil.Broker` satisfies it structurally. If you need a second event sink (e.g. logging), implement this interface rather than reaching into `sseutil` from here.

#### internal/httpapi

The REST + SSE surface, layered on top of `internal/job`, `internal/fsbrowse`, `internal/transcribe` (for model listing/health checks), and `internal/config` (including its `Settings` store, for the Settings panel's `GET`/`PUT /api/settings`). `Server` (in `server.go`) just holds those dependencies; `RegisterRoutes` (`router.go`) wires them onto a `*http.ServeMux` using Go 1.22+'s method+pattern syntax (`"POST /api/jobs"` etc.) — it does *not* create its own mux or start listening, `internal/appserver` owns that.

File-by-file:

- **`middleware.go`** — `WithMiddleware` (logging + panic recovery). Applied by `appserver` around the *whole* top-level mux (API + embedded static files), not just these routes, so a panic anywhere still gets a clean 500.
- **`respond.go`** — `writeJSON`/`writeError(Msg)` helpers. Use these, don't hand-roll `json.NewEncoder` in a new handler.
- **`health_handlers.go`**, **`browse_handlers.go`**, **`models_handlers.go`** — mostly thin wrappers calling straight into `transcribe`/`fsbrowse` and JSON-encoding the result. `health_handlers.go` and `handleModels` call `s.Config.Effective*` methods, not the plain `Config` fields, so a Settings-panel override applies immediately. `browse_handlers.go`'s `handleBrowse` takes an optional `kind` query param (`""`/`"media"` default, `"exe"`, `"dir"`) so the same endpoint backs both the original media picker and the Settings panel's ffmpeg/whisper-cli/models-directory pickers — see internal/fsbrowse above. `handleLanguages` is the one handler here that isn't a wrapper around anything: it returns a small hardcoded language list (curated common languages plus auto-detect) for the job config panel's dropdown, since whisper.cpp itself doesn't expose a "list supported languages" call worth shelling out for.
- **`settings_handlers.go`** — `GET /api/settings` returns the current overrides plus the underlying conventional defaults (so the frontend can show what "default" resolves to). `PUT /api/settings`'s request struct uses `*string` fields specifically so it can tell "field absent from the JSON body" (leave that setting untouched) apart from "field present as `""`" (explicitly clear the override back to default) — a plain `string` with `omitempty` can't make that distinction. Each non-nil, non-empty field is validated (`fsbrowse.ValidateExeFile` for the two binary paths, `fsbrowse.ValidateAbsDir` for the models directory and the default video directory) before being persisted via `s.Config.Settings.Set`. `defaultVideoDir` is reported without a matching `*Default` field in the response — unlike the other three settings it has no conventional fallback, an unset value just means "no default, list all drives."
- **`job_handlers.go`** — `handleCreateJob` is the interesting one: it validates the *entire* request before enqueueing anything — `fsbrowse.ValidateMediaFile`, then output-dir validation if `outputMode == custom`, then model lookup, then `job.OutputPrefix` + `fsbrowse.EnsureWritable` on the computed `.srt` path — and only calls `Queue.Submit` if all of that passes. The point is failing fast on a bad request instead of discovering the problem after a multi-minute transcription. If you add a new failure mode to the pipeline, check whether it can be validated here up front rather than surfacing only as a job failure. `handleListJobs`/`handleGetJob`/`handleCancelJob` are thin passthroughs to `job.Store` — see internal/job above for what its `Cancel` invariant means for the 409 case here. `handleExportJob` (`POST /api/jobs/{id}/export`) is the odd one out in this file: it acts on an already-`Done` job rather than validating-then-enqueueing — it 404s if the job doesn't exist, 409s if it hasn't reached `StatusDone` yet, validates `destDir` via `fsbrowse.ValidateAbsDir`, then `fsbrowse.CopyFile`s the job's `SRTPath` into that folder. This is purely an additive "save a copy elsewhere" action requested from the frontend's Progress tabs — it never changes or replaces the `.srt` that was already written to its original destination when the job finished.
- **`sse_handlers.go`** — `GET /api/jobs/{id}/events`. Two things worth knowing before touching this: (1) it sends the job's *current* state immediately on connect (`sseEventFromJob`), so a client that connects after the job already finished still sees the right terminal state instead of hanging forever waiting for an event that already happened; (2) it explicitly clears the response's write deadline via `http.NewResponseController(w).SetWriteDeadline(time.Time{})` and sends a heartbeat comment (`: heartbeat\n\n`) every 15s. There's no server-wide `WriteTimeout` set (see internal/appserver below and the "Cross-cutting conventions" section near the top of this file), so the explicit clear here is currently redundant *in this codebase* — but if anyone ever adds one for "hardening", this handler needs the override or long transcriptions will get their SSE connection cut mid-stream. The server's own custom `"error"` SSE event name collides with `EventSource`'s built-in connection-failure event on the frontend — see `web/src/api.ts`'s `subscribeJobEvents` for how that's disambiguated; don't rename the wire event to "fix" it without updating that too.

The server binds `127.0.0.1` only (set in `internal/appserver`, not here) — every handler in this package assumes that and returns real filesystem paths without further access control.

#### internal/webui

One file, `webui.go`: `//go:embed dist` into `var Dist embed.FS`.

This package exists *only* because Go resolves `//go:embed` patterns relative to the directory of the source file containing the directive, not the module root. `cmd/server/main.go` lives under `cmd/server/` and can't reach the repository-root `web/` directory with an embed pattern — so the directive lives here instead, in a package whose own directory sits right next to the `dist/` it embeds. `internal/appserver` is what actually mounts `webui.Dist` into the HTTP server (via `fs.Sub(webui.Dist, "dist")` plus its own SPA-fallback handler) — this package itself has zero HTTP logic.

`dist/` is generated by `cd web && bun run build` (`web/vite.config.ts`'s `build.outDir` points here, with `emptyOutDir: true`) — **never hand-edit anything under `dist/`**, it gets wiped and fully regenerated on every build. The one exception is the checked-in `dist/index.html` placeholder: it exists purely so a fresh clone's `go build ./cmd/server` succeeds *before* the frontend has ever been built (`//go:embed` fails at compile time if its target directory is empty or missing). `.gitignore` has `/internal/webui/dist/*` plus a `!/internal/webui/dist/index.html` negation to keep just that one file tracked while ignoring everything else `bun run build` produces (the placeholder gets overwritten by the real build output locally, which is expected — don't try to "fix" that by re-adding the original placeholder text after building).

#### internal/appserver

One file, `appserver.go`. `New(cfg *config.Config) (*http.Server, error)` is the single place that assembles the whole backend: builds the job `Store`/`Queue`/`sseutil.Broker`, wires the `transcribe.WhisperCppEngine` into a `job.Pipeline` (via closures over `transcribe.ExtractAudio`/`transcribe.ProbeDuration`, not direct dependencies — see internal/job above), constructs an `httpapi.Server`, and mounts it alongside the embedded frontend (`internal/webui`) with the SPA-fallback static handler.

The `WhisperCppEngine`/pipeline closures are wired to `cfg`'s `Effective*` methods (`EffectiveWhisperCliPath`, `EffectiveFfmpegPath`, `EffectiveFfprobePath`), not the plain `cfg.WhisperCliPath`/`cfg.FfmpegPath`/`cfg.FfprobePath` fields — this is what makes a Settings-panel path override take effect on the next job without restarting the process, since the single shared `engine`/pipeline is constructed once here but each method call re-reads `cfg.Settings` fresh.

It returns the `*http.Server` **without calling `ListenAndServe`** — that's deliberate, so `cmd/dev` can run it in a goroutine and `Shutdown` it later, while `cmd/server` can just call `ListenAndServe` directly. Both entrypoints call this same function; if you need to change routing, middleware, or how the pipeline is wired, do it here so neither entrypoint drifts from the other.

`spaHandler` serves the embedded `dist` filesystem and falls back to `index.html` for any path it can't find — the current UI has no client-side router so this fallback is currently unexercised, but it's the standard way to host a Vite SPA and it's free to have in place.

The `ReadHeaderTimeout`/no-`WriteTimeout` choice on the returned `*http.Server` is explained in internal/httpapi above (the SSE handler is why).

### web/

The frontend: Vite + vanilla TypeScript, deliberately no framework (React/Vue/etc.) given how small the UI is — see web/src and web/src/components below for how it's structured without one.

**Package manager is bun, not npm.** `bun.lock` is the committed lockfile; there is no `package-lock.json` (actively gitignored — see root `.gitignore` — in case npm gets run here by mistake and creates a conflicting one). Always run scripts as `bun run <script>` (`bun run dev`, `bun run build`), never the bare `bun build`/`bun install`/`bun run` shorthand for a script that happens to share a name with one of bun's own built-in subcommands — `build` is exactly such a collision here (`package.json`'s `"build": "tsc --noEmit && vite build"` would be shadowed by bun's own bundler if invoked as bare `bun build`).

Key files:

- **`index.html`** — Vite's entry point.
- **`vite.config.ts`** — dev-server proxy target for `/api` reads `process.env.FASTER_WHISPER_GUI_BACKEND_ADDR`, falling back to `127.0.0.1:8080`; `cmd/dev` sets that env var when it spawns this dev server so a custom `-addr` on the Go backend doesn't silently break the proxy. `build.outDir` points to `../internal/webui/dist`, **not** a local `web/dist/` — that's where Go's `go:embed` picks it up (see internal/webui above).
- **`tsconfig.json`** — includes `"types": ["vite/client"]`, needed for `main.ts`'s side-effect `import './styles.css'` to type-check under `tsc --noEmit` (otherwise TS has no ambient declaration for a bare `.css` import).

Build output never lives in `web/` itself — don't go looking for `web/dist/`, it doesn't exist; check `internal/webui/dist/` instead.

#### web/src

No framework — see web/src/components below for the five UI panels. This directory holds the shared plumbing they're built on:

- **`api.ts`** — typed `fetch` wrapper mirroring the Go backend's JSON shapes (`Job`, `Model`, `Listing`, `SettingsPaths`, etc. — keep these in sync with the corresponding Go structs in `internal/job`, `internal/transcribe`, `internal/fsbrowse`, `internal/httpapi`'s `settingsResponse` if the API changes) plus `subscribeJobEvents`, which wraps `EventSource` for a job's SSE stream. `browse(path, kind)` takes an optional `BrowseKind` (`'media'` default, `'exe'`, `'dir'`) matching `internal/httpapi`'s `handleBrowse` — `directoryBrowser.ts` relies on the default, `settingsPanel.ts`/`progressPanel.ts` pass `'exe'`/`'dir'` explicitly. `exportJob(id, destDir)` posts to `/api/jobs/{id}/export` — a job must already be `done`; it copies that job's already-written `.srt` into `destDir` as an additional, on-demand save, it does not change where the original was written. **The server's custom `"error"` named SSE event unavoidably shares a name with `EventSource`'s own built-in connection-failure event.** The fix here is checking `typeof (e as MessageEvent).data === 'string'` — a genuine server-sent `"error"` event always carries a JSON string payload, a native transport error doesn't. Don't try to fix this by having the browser ignore the collision differently; if the wire event name ever changes, update it on both sides (see internal/httpapi above).
- **`state.ts`** — `Store<T>`, a ~20-line pub-sub cell (subscribe gets called immediately with the current value, then again on every `set`). `selectedMedia` (checked-but-not-submitted media files), `openTabs` (jobs currently shown as a Progress tab, each carrying `{id, mediaName}`), and `activeTabId` (which tab is frontmost) are the pieces of state shared across panels; add more here rather than reaching into another component's internals.
- **`dom.ts`** — `escapeHtml`, used wherever a component interpolates a filesystem-derived string (filename, path) into an `innerHTML` template string. Windows filenames can't actually contain `<`/`>`, so this isn't defusing a realistic injection on this platform — it's cheap insurance against `&` breaking entity parsing and against relying on that platform detail at all. `basenameOf(path)` extracts a filename from a Windows- or forward-slash path — used by `jobHistory.ts` when reopening an old job as a Progress tab (a freshly-created job already has the video's `Entry.name` in hand and doesn't need it). `stripSurroundingQuotes`/`dirnameOf` are the same kind of small path helper, added for `directoryBrowser.ts`'s pasteable path input — see that file's entry in web/src/components below for why `dirnameOf` special-cases a bare drive letter.
- **`main.ts`** — wires the five panels together plus the health-check banner (`api.health()` on load, shown/hidden based on whether ffmpeg/whisper-cli probed OK).

There's no build step for this directory beyond what Vite/tsc already do — no bundler config, no path aliases, plain relative imports throughout.

#### web/src/components

Five panels, each a `mountXxx(root: HTMLElement, ...)` function called once from `main.ts`. No framework: each renders its markup via a template-string `innerHTML` assignment, then wires up plain `addEventListener` calls — there's no virtual DOM or reactive re-render, so a component that needs to update in response to state generally re-queries/mutates specific elements it already grabbed a reference to, rather than re-rendering wholesale.

- **`directoryBrowser.ts`** — a text `.drive-select` path input (despite the leftover class name, it's not a `<select>`; kept only because it reuses that class's existing CSS) + breadcrumb + entry list. The path input always mirrors `currentPath`, but also accepts free typing/pasting: Enter, blur, or a `paste` event all route through `navigateToPastedPath`, which strips quotes Explorer's "Copy as path" adds (`stripSurroundingQuotes` in `../dom.ts`) and calls `navigate`. If the cleaned path turns out to be a file rather than a directory, it retries once on `dirnameOf(cleaned)` (also `../dom.ts` — has a special case for a bare drive letter like `C:`, which Windows/Go treat as "current dir on C:" rather than the root `C:\`) so pasting a media file's path lands you in its containing folder instead of erroring. `navigate` returns the caught `Error` (or `null`) precisely so this fallback can inspect it (its other callers — row clicks, the "Up" button, the refresh button — ignore the return value). Focusing the input selects its current text, so a paste overwrites it outright, address-bar style. Clicking a directory row calls `api.browse` again; every media row (video or audio, sharing the `entry-media` class) has a checkbox, and clicking anywhere on the row (or the checkbox itself) toggles that `Entry`'s membership in the shared `selectedMedia` store (from `../state.ts`, by `path`) rather than tracking selection locally, since `jobConfigPanel` needs to read it too. Selections persist across navigation for free since `Entry.path` is absolute. A small selection-count line + "Clear" link (`.selection-bar`) lets the user see/reset what's checked while browsing. Row highlighting/checkbox state is kept in sync by comparing against the store's current value in a `selectedMedia.subscribe` callback, not by tracking DOM node identity. The row icon is 🎬 for `entry.type === 'video'` and 🎵 for `'audio'`.
- **`jobConfigPanel.ts`** — model/language dropdowns (populated from `api.models()`/`api.languages()`), output-mode radios (toggling the custom-directory `<input>`'s `disabled` state), a collapsible advanced `-ml`/max-len field, and the submit button, which reads `selectedMedia` and fires one `api.createJob` per checked file (`Promise.allSettled`, all sharing the same model/language/output config) — a batch of more than 5 files shows as "N files selected" rather than listing every name. Each successfully created job is appended to the shared `openTabs` store as `{id, mediaName}` and the first new job becomes `activeTabId`; any per-file failures are joined into the `.form-error` div. `selectedMedia` is cleared after every submit attempt, success or partial failure, so the browser panel is ready for the next batch. Validates client-side (any file selected? model selected?) before calling the API, but the server re-validates everything anyway (see internal/httpapi above) — this is just for a faster/friendlier error, not the actual guarantee. `mountJobConfigPanel` returns `{ refreshModels }` (same shape as `jobHistory.ts`'s `{ refresh }`) so `main.ts` can re-fetch the model dropdown after `settingsPanel.ts` changes the models directory, without a full page reload.
- **`progressPanel.ts`** — shows one tab per entry in the shared `openTabs` store, not just a single job. Keeps a `Map<jobId, TabState>` internally (its own live status/percent/message/srtPath/error plus an `unsubscribe` for that job's `subscribeJobEvents` connection) so a backgrounded tab keeps receiving SSE updates while a different tab is frontmost — closing a tab (the tab's `×`) is the only thing that tears its subscription down. Opening a tab (from a fresh batch, or reopened via `jobHistory.ts`) does one `api.job(id)` fetch first, since SSE only pushes *new* events, not a snapshot of a job's already-existing state. `activeTabId` selects which tab's state renders into the single shared progress bar/stage/message/cancel section. The cancel button calls `api.cancelJob` — note it does *not* optimistically update the UI, it waits for the resulting `"canceled"` SSE event to actually change the displayed state. "Save" (enabled only when the active tab's job is `done`) and "Save All Completed" (enabled when any open tab is `done`) both open an inline directory picker — built from the same drive-select/breadcrumb/entry-list pieces `settingsPanel.ts` already uses for its own `kind: 'dir'` picker, reusing its exact CSS classes but not its code — and call `api.exportJob` once (Save) or once per completed tab via `Promise.allSettled` (Save All), showing a `Saved N/M — ...` summary on partial failure. This export call is additive: the `.srt` was already written to its real destination when the job finished, `exportJob` just copies it somewhere else on demand.
- **`jobHistory.ts`** — refreshes two ways: automatically whenever `activeTabId` changes (via its own subscription, which also handles the initial load), *and* via explicit `onJobCreated`/`onJobFinished` callbacks passed in from `main.ts`. The explicit callbacks aren't redundant with the `activeTabId` subscription — a job reaching a terminal state (done/failed/canceled) doesn't change *which* tab is active, so without `onJobFinished` the history list's displayed status/percent for that row would go stale until something else happened to change `activeTabId`. Clicking a row opens (or refocuses, if already open) that job's Progress tab: if its id isn't already in `openTabs`, it's appended (labeled via `basenameOf` on the job's media path) before `activeTabId` is set to it.
- **`settingsPanel.ts`** — four text inputs (ffmpeg.exe / whisper-cli.exe / models directory / default media directory, labeled "Default Media Directory" but still backed by the `defaultVideoDir` field on the wire and in `settings.json` — deliberately not renamed, since it's an on-disk persisted setting and renaming its JSON key would silently drop an existing user's saved override on upgrade) overriding the conventional `bin/ffmpeg`/`bin/whisper`/`models` defaults (see `internal/config`'s `Effective*` methods; the default media directory has no conventional-default fallback, it's just "" until set), each with a "Browse" button opening a small inline picker built from the same pieces as `directoryBrowser.ts` (drive select + breadcrumb + entry list) but **not sharing code with it** — deliberately, matching this directory's existing pattern of self-contained panels rather than introducing a shared abstraction for one reuse. The picker's behavior differs by `kind`: `'exe'` (ffmpeg/whisper-cli fields) is click-a-file-to-select, same interaction as picking a media file; `'dir'` (the models/default-media-dir fields) has no file to click, so it shows an explicit "Select This Directory" button that selects whatever directory is currently being browsed. "Save Settings" PUTs all four fields at once (`api.updateSettings`); "Reset to Default" PUTs all four as `""`, which `internal/httpapi`'s tri-state request handling treats as "clear this override" rather than "leave unchanged" (see internal/httpapi above). Either button's `onSaved()` callback (wired in `main.ts`) re-runs the health check and `jobConfigPanel`'s `refreshModels()`.
- `directoryBrowser.ts` also reads `api.settings()` on load — if `defaultVideoDir` is set, it opens straight to that directory (and selects the matching drive in the dropdown) instead of defaulting to the first drive.

If you add a sixth panel, follow the same shape (a `mountXxx` function, own file, reads/writes `../state.ts` for anything cross-panel) rather than introducing a different pattern.
