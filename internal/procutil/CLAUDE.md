# internal/procutil

Windows-specific subprocess plumbing. Every subprocess this codebase spawns — ffmpeg, whisper-cli, and (in `cmd/dev`) `bun run dev` — should go through `Start` here, not a bare `cmd.Start()`.

- **`linesplit.go`** — `ScanCRLines`, a `bufio.SplitFunc` (used via `NewCRLineScanner`) that treats a bare `\r` as a line terminator in addition to `\n`. whisper-cli's progress output redraws in place using `\r` the way a classic CLI progress bar does; `bufio.ScanLines` only splits on `\n`, so those updates would sit in the buffer — invisible — until the next real `\n` arrives, which looks like "progress stalls for a few seconds then jumps." This is a pure, well-tested function (`linesplit_test.go`) — if progress parsing elsewhere seems to skip lines, check whether it's reading through this scanner or a plain one.
- **`jobobject_windows.go`** — `JobObject` wraps `CreateJobObject`/`SetInformationJobObject` (with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) / `AssignProcessToJobObject` / `TerminateJobObject`. The payoff: killing or closing the job takes down *every* process assigned to it, including grandchildren the direct child spawns — plain `cmd.Process.Kill()` only ever reaches the direct child. This has been verified by hand against a real multi-level tree (`dev.exe` → `bun.exe` → `node.exe`): force-killing the top process alone still cleans up the whole chain, because `KILL_ON_JOB_CLOSE` fires when the job handle is reclaimed on process exit, with no cooperation from the dying process required. Note `AssignProcessToJobObject` requires `PROCESS_SET_QUOTA|PROCESS_TERMINATE` access, obtained here via `OpenProcess` by PID immediately after `cmd.Start()` — not a flag on `CreateProcess` itself.
- **`managed_windows.go`** — `ManagedProcess`/`Start(cmd)` ties the two together: starts `cmd`, creates a `JobObject`, assigns the new process to it. If job-object creation/assignment fails (e.g. this program is itself running inside some restrictive parent job/container that denies nesting), it logs a warning and **degrades to plain `cmd.Process.Kill()`** rather than treating it as fatal — job-object cleanup is a safety net, not a correctness requirement, so a restricted environment shouldn't crash the whole program over losing it.

If you add a new subprocess call anywhere in the codebase, route it through `procutil.Start`, and if you need to read its output for progress/diagnostics, read it through `NewCRLineScanner` rather than a plain `bufio.Scanner`.
