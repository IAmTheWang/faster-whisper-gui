# internal/httpapi

The REST + SSE surface, layered on top of `internal/job`, `internal/fsbrowse`, `internal/transcribe` (for model listing/health checks), and `internal/config` (including its `Settings` store, for the Settings panel's `GET`/`PUT /api/settings`). `Server` (in `server.go`) just holds those dependencies; `RegisterRoutes` (`router.go`) wires them onto a `*http.ServeMux` using Go 1.22+'s method+pattern syntax (`"POST /api/jobs"` etc.) — it does *not* create its own mux or start listening, `internal/appserver` owns that.

File-by-file:

- **`middleware.go`** — `WithMiddleware` (logging + panic recovery). Applied by `appserver` around the *whole* top-level mux (API + embedded static files), not just these routes, so a panic anywhere still gets a clean 500.
- **`respond.go`** — `writeJSON`/`writeError(Msg)` helpers. Use these, don't hand-roll `json.NewEncoder` in a new handler.
- **`health_handlers.go`**, **`browse_handlers.go`**, **`models_handlers.go`** — mostly thin wrappers calling straight into `transcribe`/`fsbrowse` and JSON-encoding the result. `health_handlers.go` and `handleModels` call `s.Config.Effective*` methods, not the plain `Config` fields, so a Settings-panel override applies immediately. `browse_handlers.go`'s `handleBrowse` takes an optional `kind` query param (`""`/`"media"` default, `"exe"`, `"dir"`) so the same endpoint backs both the original media picker and the Settings panel's ffmpeg/whisper-cli/models-directory pickers — see `internal/fsbrowse/CLAUDE.md`. `handleLanguages` is the one handler here that isn't a wrapper around anything: it returns a small hardcoded language list (curated common languages plus auto-detect) for the job config panel's dropdown, since whisper.cpp itself doesn't expose a "list supported languages" call worth shelling out for.
- **`settings_handlers.go`** — `GET /api/settings` returns the current overrides plus the underlying conventional defaults (so the frontend can show what "default" resolves to). `PUT /api/settings`'s request struct uses `*string` fields specifically so it can tell "field absent from the JSON body" (leave that setting untouched) apart from "field present as `""`" (explicitly clear the override back to default) — a plain `string` with `omitempty` can't make that distinction. Each non-nil, non-empty field is validated (`fsbrowse.ValidateExeFile` for the two binary paths, `fsbrowse.ValidateAbsDir` for the models directory and the default video directory) before being persisted via `s.Config.Settings.Set`. `defaultVideoDir` is reported without a matching `*Default` field in the response — unlike the other three settings it has no conventional fallback, an unset value just means "no default, list all drives."
- **`job_handlers.go`** — `handleCreateJob` is the interesting one: it validates the *entire* request before enqueueing anything — `fsbrowse.ValidateMediaFile`, then output-dir validation if `outputMode == custom`, then model lookup, then `job.OutputPrefix` + `fsbrowse.EnsureWritable` on the computed `.srt` path — and only calls `Queue.Submit` if all of that passes. The point is failing fast on a bad request instead of discovering the problem after a multi-minute transcription. If you add a new failure mode to the pipeline, check whether it can be validated here up front rather than surfacing only as a job failure. `handleListJobs`/`handleGetJob`/`handleCancelJob` are thin passthroughs to `job.Store` — see `internal/job/CLAUDE.md` for what its `Cancel` invariant means for the 409 case here. `handleExportJob` (`POST /api/jobs/{id}/export`) is the odd one out in this file: it acts on an already-`Done` job rather than validating-then-enqueueing — it 404s if the job doesn't exist, 409s if it hasn't reached `StatusDone` yet, validates `destDir` via `fsbrowse.ValidateAbsDir`, then `fsbrowse.CopyFile`s the job's `SRTPath` into that folder. This is purely an additive "save a copy elsewhere" action requested from the frontend's Progress tabs — it never changes or replaces the `.srt` that was already written to its original destination when the job finished.
- **`sse_handlers.go`** — `GET /api/jobs/{id}/events`. Two things worth knowing before touching this: (1) it sends the job's *current* state immediately on connect (`sseEventFromJob`), so a client that connects after the job already finished still sees the right terminal state instead of hanging forever waiting for an event that already happened; (2) it explicitly clears the response's write deadline via `http.NewResponseController(w).SetWriteDeadline(time.Time{})` and sends a heartbeat comment (`: heartbeat\n\n`) every 15s. There's no server-wide `WriteTimeout` set (see `internal/appserver`/root CLAUDE.md), so the explicit clear here is currently redundant *in this codebase* — but if anyone ever adds one for "hardening", this handler needs the override or long transcriptions will get their SSE connection cut mid-stream. The server's own custom `"error"` SSE event name collides with `EventSource`'s built-in connection-failure event on the frontend — see `web/src/api.ts`'s `subscribeJobEvents` for how that's disambiguated; don't rename the wire event to "fix" it without updating that too.

The server binds `127.0.0.1` only (set in `internal/appserver`, not here) — every handler in this package assumes that and returns real filesystem paths without further access control.
